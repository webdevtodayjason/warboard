1. What we built

WARBOARD is a live OSINT world-news board where every drop of AI runs on a Tiiny Pocket — a palm-sized edge appliance with an NPU. No cloud inference is called, ever.

  • Ingest: 27 free feeds — world wires, conflict reporting, CISA cyber advisories, NWS severe weather, USGS seismic, GDACS disasters, volcanic activity, defense and aviation — polled continuously.
  • Analysis (Ornith-1.0-35B, 50 NPU units): every article gets a one-line summary, a category, a combatant-command region (NORTHCOM/EUCOM/CENTCOM/AFRICOM/INDOPACOM/SOUTHCOM/GLOBAL) and a severity S1–S5.
  • Clustering (Qwen3-Embedding-0.6B, 1 unit): every item is embedded on-device; cosine similarity fuses cross-source coverage into "developing stories," which Ornith then titles.
  • Imagery (Z-Image-Turbo, 32 units): click any article and the device paints a photorealistic editorial illustration in about eight seconds.
  • Archive: the pipeline files daily intelligence digests into the device's own Knowledge Base, and a public "Ask the Archive" box performs semantic retrieval against that on-device vault.
  • Telemetry: live NPU load, thermals, tokens burned, an AI ops log narrating every action as it happens, and an infrared rack camera pointed at the device doing the work.

All three models are resident simultaneously — 83 of the device's 100 NPU units — scheduled against each other in real time. The backend is pure Python standard library; the front end is a single HTML file. It runs on an Orange Pi 6 Plus in a server rack and publishes through a Cloudflare tunnel.

3. The headline failure: a headless device cannot unlock itself

Root cause

The Tiiny's user data lives on an encrypted volume that is opened by POST /api/v1/account/auth with {"password": "<master password>"} — a call the TiinyOS desktop app makes automatically when it connects. With no app present, nothing makes that call, so the device boots with the volume closed: no gateway, no models, no AI stack. The base OS runs fine, which is what makes it confusing — the device looks healthy and answers SSH while being functionally dead.

Two details turn an inconvenience into a deployment blocker:

  • The documented endpoint does not exist on shipping firmware. The public SDK documentation shows POST /api/v1/auth/login on port 80. On our unit that path returns 404 Not Found. The neighbouring /api/v1/account/auth on port 80 returns 410 Gone with a message that names the real answer: "Account APIs have migrated to authd. Use authd account and token flows." — so the device knows the documentation is stale even though the docs site does not.
  • The real endpoint is loopback-only. authd listens on 127.0.0.1:6666 and nowhere else, so no remote host can unlock the device. The call has to originate on the device itself.

Our workaround, now running in production: the rack host holds the device's SSH key and its master password in a root-only environment file, and a systemd timer checks every three minutes. If the gateway is dark, it SSHes into the device, performs the unlock on loopback, waits for the container stack, then loads all three models and lets the pipeline drain its backlog. First real test passed — the device went from locked to fully operational with no human involved.

Why this matters beyond us

Every drop-box, kiosk, branch-office and client-site deployment has the same shape: the device is somewhere nobody visits, and power events happen. As shipped, a Tiiny in that role stays dark until a person arrives with a laptop. The fix on the vendor side is small — persist the unlock across reboots, or expose the auth endpoint on the device's network interfaces so an orchestrator can do it — but until then, unattended deployment is not possible without root access to the device.

4. What broke, and what it taught us

Power delivery is not a solved problem

The first hours were lost to a USB dock browning out: a gigabit ethernet adapter and a 512 GB drive on one bus-powered hub produced 20 disconnects in 42 minutes. Three fixes, in order of surprise: the 140 W Apple brick would not power the device on at all (PD profile mismatch) while the 67 W brick does; the dock needs its own supply rather than drawing through the device's port budget; and the residual whole-hub drops were a bad USB-C cable. After the swap: eight minutes hands-off at zero disconnects.

Lesson: whole-hub re-enumeration means cable or connection, not power. Per-device drops mean power. The kernel ring buffer tells you which in seconds.

An appliance that looks healthy can be completely dead

Every failure tonight presented identically: SSH works, uptime climbs, the app shows a dashboard — and nothing functions. The device knows its state perfectly and exposes almost none of it. That is the same pattern as three-quarters of the bugs filed during this beta: internal state that never reaches the user.

Three subnets will waste an hour of your life

The workstation, the rack, and the device's own Wi-Fi were on different networks. Several "the device vanished" moments were scans of the wrong subnet. What saved the deployment was building on paths that do not depend on addressing: a Tailscale overlay for management, and a USB point-to-point link (172.17.7.176/30) between the host and the device that no DHCP lease can disturb.

The public board never went down during any of it, because the tunnel dials outbound and the data path is a cable.

Multi-model NPUs need client-side scheduling

Running chat, embeddings and image generation on one NPU works — but a Z-Image request issued while Ornith is mid-inference fails with device error 150004. There is no queue on the device, so the application has to provide one. WARBOARD coordinates with a lease in its database: the pipeline yields before image generation, image requests wait out in-flight enrichment, and viewer clicks always win.

Verify every feed before you ship it

Of 14 candidate sources added in the second wave, one had a broken certificate chain and was dropped before deploy. Later, Times of Israel began returning 403 to every user agent we tried, from three different networks and from the device itself — a CDN bot wall, not something to fight. Jerusalem Post replaced it. Feed errors now log once on failure and once on recovery instead of every cycle.

Headline findings

1. #041, a headless unit cannot unlock its own data volume, so it cannot survive a power event. The unlock is POST /api/v1/account/auth to authd with body {"password":"<master password>"}, and authd binds 127.0.0.1:6666 only, so the call has to originate on the device. This supersedes the heartbeat theory in the original report: no remote host, no monitoring system, and no orchestrator can unlock the box, which means every power cut leaves a rack-mounted unit dark until a human intervenes. The only working recovery today is an external machine that holds an SSH key and the device master password in cleartext and shells in to curl loopback, which is a worse security posture than the vendor shipping a real unattended-unlock option.

2. #040, knowledge base retrieval has no privacy boundary. /kb/retrieve searches one flat namespace with one API key, mixing uploaded files, the preloaded user guide, and automatic daily summaries of the owner's private Chat conversations. An unattended device is exactly the case where retrieval is exposed to something else, a dashboard, an agent, or an MCP tool, and the owner is not watching what comes back. This already leaked a private conversation summary into a public-facing feature in testing, and client-side filename filtering is a workaround rather than a boundary. Source scoping on the query, per-source visibility flags, private-by-default conversation summaries, and per-integration scoped keys would each close part of it.

3. #025, the tester feedback sheet is world-readable and world-writable. Its permissions are {"role":"writer","type":"anyone"}, confirmed against the Drive API and proven writable from an unrelated service account. It currently holds fourteen unpatched findings against shipping hardware, four marked CRITICAL, with reproduction steps, which is a ready-made attack guide for any fleet of these devices sitting unattended in racks and offices. The link only has to leak once and the exposure cannot be revoked retroactively, so this needs restricting to named accounts and an audit of every other tester sheet built from the same template.

4. #038, there is no way to address the device except through a host-level DNS hack. The app resolves api.tiiny only because pcsvr writes /etc/resolver entries on the paired Mac, and if that entry is missing, disabled, or stale the app shows "Failed to connect device" with no manual host or IP override anywhere in the UI. In this case the tester had disabled the resolver himself, so the finding is not that pcsvr failed, it is that a fully reachable device (answering on IP and on SSH) becomes unmanageable from the app with no recovery path. An unattended deployment is LAN-only by definition, with no USB host and no desktop app on the subnet, which the current connection model does not support at all.

5. #022, loading a model silently evicts models that did not need evicting. Starting a 55-unit model cleared both a 47-unit model, which genuinely had to go, and a 1-unit embedding model, which fitted in the 45 units left over. Nothing anywhere reports the eviction, so an unattended deployment loses its embeddings or OCR endpoint mid-flight because somebody picked a different model in a chat dropdown. The device already exposes GET /api/v1/models/{id}/unload_candidate, which appears purpose-built to answer exactly this question, and the vendor's own chat assistant confirms multi-model residency is intended, so this is a defect rather than a design limit.

6. #028, the device does not reliably rejoin a saved network and never says why. A remembered SSID with auto-connect enabled, sitting at signal 100, was not joined, and connection_status returned is_connected: false with error: null. The 17 Aug follow-up confirms it does auto-join sometimes, and the tester's hypothesis is that losing an association in place fails to trigger a rescan while a clean power-down and move does. For a Wi-Fi-only appliance left in a rack, an association that drops and never re-establishes means the unit is simply gone, and the null error field means there is nothing to alert on even if something is watching.

Just below the line: #033 (Qwen's own official repo, advertised as supported, cannot be imported because shard names are pattern-built instead of read from model.safetensors.index.json) and the #034 + #036 pair (a dead import is drawn as a live download, and its three retries are spent in 32 seconds on a transient 403). Together those make unattended provisioning fail silently and permanently.

B. Prepare the Tiiny device

B1. Activate and get the API key

  1. Power the device on bare — no dock, no hub. Give it ~2 minutes.
  2. Complete first-run setup in the TiinyOS desktop app; set the master password. Record the account username and password — WARBOARD needs both later (TIINY_USER, TIINY_PASS).
  3. Settings → API key. Copy the UUID. This one static key authorizes everything on the device, including Docker control. Treat it as a root credential.

B2. The unlock reality [FIRMWARE]

The device boots with its encrypted data volume closed. The AI stack (the whole Docker compose set behind :8800) does not exist until /dev/mapper/userdata_crypt appears.

  • The TiinyOS desktop app performs the unlock automatically when it connects. Headless there is nobody to do that, so after every power event the gateway stays dark forever.
  • The unlock is POST /api/v1/account/auth with body {"password": "<master password>"} against authd.
  • authd listens on 127.0.0.1:6666 ONLY. Verified from the Pi: port 6666 is closed from off-device; nginx on :80 answers that path with 410 Gone (“migrated to authd”). Therefore the unlock call must be executed ON the device over SSH. This is the single non-obvious fact in the whole build.
  • Success returns a JSON body containing attestation; /dev/mapper/userdata_crypt appears and compose brings the stack up over the next ~30–300 s.

B3. SSH into the device (needed for §F) [FIRMWARE]

Port 3588, publickey only, user tiiny, root locked.

# from the Pi, generate a dedicated key for this purpose
sudo ssh-keygen -t ed25519 -N '' -f /etc/warboard-tiiny.key -C warboard-wake
sudo chmod 600 /etc/warboard-tiiny.key
sudo ssh-keygen -y -f /etc/warboard-tiiny.key      # -> ssh-ed25519 AAAA...

Install that public key into /home/tiiny/.ssh/authorized_keys on the device (via the desktop app terminal, an existing SSH session, or the Docker Compose Manager on :8880). Then verify:

sudo ssh -n -i /etc/warboard-tiiny.key -p 3588 -o BatchMode=yes \
  -o StrictHostKeyChecking=no tiiny@172.17.7.177 'echo OK; ls /dev/mapper/'
# expect: OK  /  control  userdata_crypt

[FIRMWARE] /home is an OverlayFS over a RAUC A/B slot. A firmware update can wipe authorized_keys. Re-install the key after every device update or the wake watchdog silently stops working.

Loading them:

load-models.sh percent-encodes the model id (Qwen%2FQwen3-Embedding-0.6B) — percent-encoding is optional on current firmware — a literal slash also returns 200. Download budget in the script is 2400 s for ~1.2 GB; start budget 300 s. Model loads take 30–90 s each.

Device behaviour that shapes the whole design:

  • No batching. One inference at a time, ~24 tok/s. Enrichment is a strictly serial queue; parallelising makes it slower.
  • Chat and image generation cannot overlap. A concurrent request returns device error 150004. server.py and pipeline.py negotiate through two DB meta keys — img_hold_until and enrich_busy_until — plus a 3-attempt retry with 6 s gaps.
  • Ornith reasoning quirk. Reasoning lands in message.reasoning_content and counts against max_tokens, leaving content empty. enrich.py sends chat_template_kwargs.enable_thinking=false first (~50 tokens, 5–24 s), and only on failure retries with reasoning on at 2400 tokens, scavenging the trailing {...} from the reasoning trace. TIINY_NOTHINK=0 disables the fast path.
  • 512×512 is the only resolution Z-Image-Turbo produces on this firmware. The UI crops to 16:9 with object-fit.

D4. Camera device path — this is the trap

/dev/video0 through /dev/video3 are the CIX SoC codec engine, not a camera. The USB cam enumerates as video4. If ustreamer is pointed at a codec node it streams a NO SIGNAL placeholder forever and never errors.

ls -l /dev/v4l/by-id/
# usb-InnoMaker_Innomaker-U20CAM-1080PD_N-S1_20010101-video-index0 -> ../../video4
# usb-InnoMaker_Innomaker-U20CAM-1080PD_N-S1_20010101-video-index1 -> ../../video5

Always use the by-id path — it survives node renumbering across reboots. index0 is the capture node; index1 is metadata.

warboard-camera.service as shipped (and as running):

ExecStartPre=-/usr/bin/v4l2-ctl -d /dev/v4l/by-id/usb-InnoMaker_Innomaker-U20CAM-1080PD_N-S1_20010101-video-index0 \
  --set-ctrl=brightness=0 --set-ctrl=contrast=38 --set-ctrl=gamma=300 --set-ctrl=gain=32 \
  --set-ctrl=backlight_compensation=0 --set-ctrl=auto_exposure=3
ExecStart=/usr/bin/ustreamer -d /dev/v4l/by-id/usb-InnoMaker_Innomaker-U20CAM-1080PD_N-S1_20010101-video-index0 \
  -m MJPEG -r 1280x720 -f 15 --host 127.0.0.1 -p 8812

The v4l2-ctl line is not cosmetic: UVC defaults drift to max gain/gamma and the frame comes back blown-out white. The - prefix makes it non-fatal.

--host 127.0.0.1 is load-bearing — only server.py may reach the camera; the browser gets it proxied through /cam.mjpg.

[DIVERGENCE] install.sh's "pin ustreamer" drop-in path writes ExecStart=... -d /dev/video0 ..., discarding both the by-id path and the sensor tuning. It does not fire on this host (ustreamer is at /usr/bin), but on a host where ustreamer lives elsewhere it silently breaks the camera. Patch the drop-in template before using it on new hardware.

Different camera model? Get your own id:

v4l2-ctl --list-devices
ls /dev/v4l/by-id/            # pick the *-video-index0 entry for the capture node
v4l2-ctl -d <by-id path> --list-ctrls   # then retune brightness/contrast/gamma/gain

F. Make it survive power loss

The failure mode: mains blips → Tiiny reboots → encrypted volume closed → :8800 dark → warboard-pipeline backs off forever. Nothing recovers on its own, because the unlock is normally done by a desktop app that isn't there.

Three pieces, none of which install.sh handles. [DIVERGENCE] — all installed by hand on the live box.

1. The device SSH key on the host — /etc/warboard-tiiny.key, 0600 root:root, ed25519 (§B3). Required because the unlock call has to originate on the device: authd binds 127.0.0.1:6666 only, and nginx on :80 answers that path with 410 Gone (“migrated to authd”). There is no remote way to do it.

2. The watchdog script — /opt/warboard/deploy/wake-check.sh (0755 root). Every tick it:

GET  http://$TIINY_HOST:8800/api/v1/models/npu/status   (5 s)
  != 200 and TIINY_PASS set
    -> ssh -i /etc/warboard-tiiny.key -p 3588 tiiny@$TIINY_HOST
         curl -X POST -d @- http://127.0.0.1:6666/api/v1/account/auth   ({"password": "..."})
       response contains "attestation" -> poll the gateway for up to 300 s
  still != 200 -> exit 0, retry next tick
  == 200 and fewer than 3 models running
    -> bash /opt/warboard/deploy/wake-tiiny.sh $TIINY_HOST

The password is marshalled through python3 -c 'json.dumps(...)' via an env var, never interpolated into the shell. All output appends to /var/log/warboard-wake.log.

3. The unit + timer:

sudo install -o root -g root -m 0644 /opt/warboard-src/deploy/warboard-wake.service /etc/systemd/system/
sudo install -o root -g root -m 0644 /opt/warboard-src/deploy/warboard-wake.timer   /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now warboard-wake.timer
systemctl list-timers warboard-wake --no-pager

Type=oneshot, EnvironmentFile=/etc/warboard.env, OnBootSec=2min (matches the device's ~2 min unlock window after power-on), OnUnitActiveSec=3min.

Manual recovery, if you'd rather drive it yourself:

TIINY_KEY=<key> bash /opt/warboard/deploy/wake-tiiny.sh 172.17.7.177

Waits up to 300 s for the gateway, starts all three models, waits up to 200 s for RUNNING, then proves chat + embeddings + image generation. It does not perform the authd unlock — do that first, or let wake-check.sh do it.

Once the models are back, warboard-pipeline recovers on its own within ~5 minutes; sudo systemctl restart warboard-pipeline if you're impatient.

Optional evidence collector, on the live box only:

sudo nohup /opt/warboard/deploy/relock-probe.sh &   # -> /var/log/tiiny-relock.log

Tuning constants you should not move casually

  • enrich.CLUSTER_THRESHOLD = 0.80 cosine. Measured 2026-08-21 against the live embedder over 89 enriched articles (3,916 pairs): every pair ≥0.808 was a genuine same-story match, the next one down at 0.774 was junk, and it sat between genuine matches at 0.724 and 0.720. The 0.72–0.78 band is mixed — lowering it buys two real joins and one visibly wrong story on the DEVELOPING panel. Re-run that measurement over a few hundred live items before touching it.
  • Embeddings are optional. If the embedder won't load, clustering falls back to normalized-title Jaccard ≥0.55 and meta.embeddings goes off, which the bottom bar surfaces. The pipeline never stops.
  • Every network call has a timeout and a try/except. A dead feed, a Tiiny timeout, or a malformed article gets logged and skipped. Keep it that way — this runs a week with nobody watching.
