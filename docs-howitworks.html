1The whole system on one page

The split is deliberate: the Orange Pi does everything that is not thinking — fetching, parsing, storing, serving, streaming, publishing — and the Tiiny does nothing but think. No inference call leaves the rack. The two talk over a cable.

WARBOARD is a reference implementation of the Tiiny platform. It speaks to the device over its documented HTTP API with no client library and no third-party packages — Python's standard library and nothing else — and it drives five of the nine model classes the hardware ships with, concurrently, on one pocket-sized NPU.

2Networking: a cable and an outbound tunnel

The data path is a USB cable, not the LAN

The Tiiny presents a USB Ethernet gadget. Plugged into the Pi, that creates a two-host network:

Pi   enx02ce2881f302  172.17.7.178/30  ──USB──  172.17.7.177  usb0   Tiiny

A /30 is four addresses: network, two hosts, broadcast. There is no room for anyone else and no DHCP server involved. That decision paid for itself the same night it was made — the rack moved to a new subnet, the device's LAN adapter came and went, its Wi-Fi landed on a third network entirely, and the pipeline never noticed, because its peer address is a property of the cable rather than of the building.

The public URL opens no ports

cloudflared runs on the Pi and dials out to Cloudflare, then serves requests back down that established connection. Nothing listens on the public internet; the web server is bound to 127.0.0.1:8811 and is not reachable from the LAN at all.

tunnel: c38fb8dd-…
ingress:
  - hostname: warboard.semfreak.dev
    service: http://localhost:8811
  - service: http_status:404
Why this is the right shape for an appliance

No port forwarding, no static IP, no firewall holes, no certificate management — TLS terminates at Cloudflare's edge. Move the hardware to a different building on a different ISP and the URL follows it, because the tunnel is outbound. Setup is one browser click to authorize the domain, one command to create the tunnel, one to route DNS.

Management access follows the same philosophy: the Pi is on a Tailscale overlay, so administration works from anywhere without exposing SSH. Three different network paths existed at various points tonight; the public board never went down.

That is 85 units held continuously with 15 spare, briefly reaching 92 while a brief is being narrated. *Speech is not resident: it is started for a narration run and released after, which is how a fifth model fits at all. Loading them is trivial; using them concurrently is not.

The concurrency problem, and the lease that solves it

An image request issued while the chat model is mid-inference fails with device error 150004. There is no queue on the device — the application has to be the queue.

WARBOARD coordinates through two keys in its own database. The pipeline publishes enrich_busy_until while a chat call is in flight; a viewer clicking an article takes img_hold_until before generating. Each side yields to the other's flag, and the enricher checks between every item rather than mid-batch, so a click waits at most one article. Idle background work — the hourly situation report, pre-rendering images for severe stories — honours the same lease and always loses to real traffic.

The result is a device that stays busy without ever colliding with itself: enrichment first, then reporting, then speculative imagery, and a human click preempts all of it.

4The enrichment pipeline

Four supervised threads, each with its own SQLite connection (WAL mode lets the web server read while the pipeline writes). Every loop iteration is individually wrapped: a failure logs one line and backs off exponentially, never killing the thread. This has to run for a week without supervision.

fetch    27 feeds every 5 min → dedupe by URL → insert
enrich   serial queue → Ornith → validate → embed → cluster → metrics
device   NPU/CPU/memory telemetry every 5 s
vault    daily intel digest filed into the device Knowledge Base
sitrep   hourly situation report + idle-time image pre-rendering
janitor  prune hourly (items 21 d, metrics 8 d, oplog 48 h)

Getting structured data out of a reasoning model

Ornith puts its chain of thought in message.reasoning_content, and that content counts against max_tokens. Ask for JSON with a small budget and you get an empty content field and a finish_reason of length — the model spent the entire allowance thinking. The client handles it three ways: a generous 800-token budget, an explicit request to disable thinking, and if content still comes back empty, it scavenges the last complete JSON object out of the reasoning text.

The prompt itself is a strict schema with closed enums — eleven categories, seven combatant-command regions, and a severity rubric written as a rubric rather than a vibe:

5 = mass casualty / major attack / war escalation / nuclear
4 = significant armed action / major disaster / coup
3 = notable political-security development
2 = routine geopolitics or economy
1 = low signal

Every field is validated after parsing; enums outside the list are rejected and severity is clamped. An article that fails parsing is retried, then parked with the real error message — and re-queued automatically after ten minutes, up to three attempts, so a transient device hiccup never permanently buries a story.

5Clustering: the 0.80 threshold we measured

When four outlets cover the same event, the board should show one developing story, not four rows. Each article's embedding is compared by cosine similarity against recent members of clusters touched in the last 72 hours; above the threshold it joins, otherwise it starts a new one. Once a cluster reaches three members, Ornith writes it a headline.

The interesting part is the threshold, which was measured rather than guessed. Against the live embedder: 89 real enriched articles off the running feed set, 3,916 real pairs, embedded exactly the way the pipeline does it.

What the corpus showed

Every pair at or above 0.808 was a genuine same-story match — ten of them, spanning BBC, Guardian, Al Jazeera and France24. The next pair down, 0.774, was junk: "Israeli settler attacks in the West Bank" against "Labour stalling on Jackdaw and Rosebank." And it sat between two genuine matches at 0.724 and 0.720.

So the 0.72–0.78 band is genuinely mixed — no threshold inside it separates signal from noise. 0.80 is the clean cut.

An earlier pass had lowered it to 0.72 based on a 55-pair hand-picked sample that under-represented the unrelated tail, and on the full corpus that put a visibly wrong story on the board. The asymmetry matters on a wall display: a missed join just leaves two items on the wire; a false join invents a developing story and hangs an AI-written headline on it.

If the embedding model is ever unavailable, clustering degrades to title-token overlap (Jaccard ≥ 0.55) and the board reports embeddings: off rather than silently changing behaviour.

6Painting the news

Click any headline and the drawer asks the device for an illustration. The call uses the native image route rather than the OpenAI-compatible wrapper, which lets us pass diffusion parameters directly:

POST /v1/image/generate
{ "model":"Tongyi-MAI/Z-Image-Turbo", "prompt": …, "negative_prompt": …,
  "width":512, "height":512, "seed": <item id>, "steps":8 }   → raw PNG
  • Seed = the article's database id, so a story's image is deterministic. Regenerate it a year later and you get the same picture.
  • 512×512 is not a style choice. The model card advertises 1024×1024, 768×432 and others as verified; on shipping firmware every size except 512×512 fails after a flat ~30 s with device error 150004, NPU idle. Only the native graph appears to have shipped. The board crops the square to 16:9.
  • Prompting matters. The first version said "editorial news illustration for this headline," and the model dutifully painted newspaper signage covered in garbled pseudo-text. Describing the scene instead, with writing surfaces in the negative prompt, fixed it.
  • Cached forever on disk, keyed by id, so a popular story costs one generation.

7The on-device archive

The device has a Knowledge Base — a vault with semantic retrieval — and WARBOARD feeds it. Every day the pipeline writes an intelligence digest of that day's enriched items, grouped by region with the developing stories appended, and files it:

POST /kb/upload      (multipart)  → source_id
POST /kb/finalize    {source_id}  → indexed, vectorised on-device
POST /kb/retrieve    {question}   → semantically ranked passages

A public "Ask the Archive" box on the board runs that retrieval, so anyone can query months of on-device analysis in plain language. The vault also holds a project brief, which means the board can answer questions about itself.

A privacy boundary we had to build ourselves

/kb/retrieve searches one flat namespace with no scoping parameter — user files, app-filed documents, and the device's automatic summaries of the owner's private chat conversations, all ranked together. The first public retrieval test returned a summary of a personal conversation. The public endpoint is now scoped server-side to WARBOARD's own filings, and the underlying gap was filed with the vendor as a security request: retrieval needs source filtering, per-source visibility, and conversation summaries private by default.

8Making the AI legible

An AI appliance that works silently is indistinguishable from one that has died. The board therefore narrates itself. A now_doing key holds a single human sentence for whatever is in flight, and an append-only oplog table records each completed action:

21:44:53  ENRICH   #342 S3 AFRICOM/disaster 24.5 tok/s — Tchad: 7M USD pour…
21:44:46  SITREP   watch officer filed hourly SITREP (30 wire items reviewed)
21:44:35  VAULT    filed warboard-intel-2026-08-21.md (50 entries indexed)
21:45:24  IMAGE    auto-rendered S4+ story #330 — Kryvyi Rih shopping centre

Two design notes that came out of watching it run. Feed failures log on state change only — once when a source goes down, once when it recovers — because a persistently broken feed reporting every five minutes buries everything else. And the NPU telemetry poll had to drop from 30 s to 5 s: an image generation is an 8-second spike, and a 30-second sampler simply never saw it, so the gauge read zero while the device was at 100%.

9The rack camera

An IR day/night USB camera watches the Tiiny while it works. ustreamer encodes MJPEG bound to loopback, and the web server proxies it — the camera is never exposed, and a dead camera returns a fast 503 instead of hanging a browser connection.

Three lessons, each a wasted half hour:

  • Find the right node. /dev/video0–3 on this host are the SoC's hardware video codec, not the webcam. The camera was /dev/video4, and ustreamer happily streamed a "NO SIGNAL" placeholder from the wrong device. The service now uses the stable /dev/v4l/by-id/… path so node renumbering after a reboot cannot break it.
  • Browsers never fire onload for multipart/x-mixed-replace. Liveness cannot come from the <img> element; a separate snapshot probe is the authority, with automatic fallback to 1 fps snapshot polling if a CDN ever refuses the stream.
  • UVC controls drift. The sensor had wandered to maximum gain, gamma and backlight compensation — a pure white frame. Sane values are now applied by an ExecStartPre= line, so a restart always re-establishes them.

10Self-healing

The deployment target is "a box in a rack that nobody visits," so every recovery path is automated. A systemd timer runs every three minutes and walks a ladder:

  1. Is the device's data volume open? If not, unlock it. On this firmware the encrypted volume is opened by an authd call the desktop app normally makes — headless, nobody makes it, and the unlock endpoint is bound to 127.0.0.1 on the device, so the call has to originate on the device. The watchdog SSHes in with a key and does it.
  2. Are all three models running? If not, start them and verify chat, embeddings and image generation each answer.
  3. Has the device moved? A discovery sweep finds it and rewrites the configuration.

Everything else is ordinary systemd: five units, all Restart=always, all enabled at boot. The pipeline treats device outages as expected — exponential backoff, no queue burning, automatic resume. Its first unattended test came the same night: a power event left the device locked, and it went from dark to fully operational with nobody in the room.

11The constraints that paid off

Python standard library only zero dependencies

No pip, no virtualenv, no lockfile, no supply chain. sqlite3, urllib, xml.etree, http.server, struct, threading — that is the entire stack. Deployment is copying files. Nothing can break because an upstream package changed, and there is no build step to fail at 3 a.m.

One HTML file no framework

The board is a single self-contained document: no CDN, no bundler, no npm. Canvas sparklines and gauges are drawn by hand. It renders correctly with zero items and with two hundred, and it loads instantly over a tunnel because it is one request.

Security posture

  • The device key never reaches the browser. Every device call is server-side; the front end talks only to our own /api/*.
  • Feeds are hostile input. Article titles are escaped on output, and URLs are validated against ^https?:// at three layers — the parser, the database insert, and the renderer — after a review pass caught that a feed could inject a javascript: link.
  • Bounded everything. 4 MB cap per feed body, timeouts on every network call, retention limits on every table, and a semaphore on camera streams.
Boring on purpose

Nothing here is clever. A cable instead of a network, an outbound tunnel instead of a firewall rule, a flat file database, a single HTML page, and a shell script on a timer. The interesting part of the project is what runs on top: three models on a device you can hold in one hand, reading the world's news at 24 tokens a second, all night, unattended.
